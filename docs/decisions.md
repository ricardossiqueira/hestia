# Decisões de arquitetura

| ID | Decisão | Motivo |
| --- | --- | --- |
| ADR-001 | Go no gateway | Binário único, baixo uso de recursos e boa concorrência. |
| ADR-002 | Mosquitto como broker local | Maduro, pequeno e separa broker da lógica de domínio. |
| ADR-003 | YAML como cadastro de dispositivos | Fácil de revisar e adequado ao conjunto inicial pequeno e estável. |
| ADR-004 | SQLite como outbox | Persistente, sem serviço adicional e apropriado ao Orange Pi. |
| ADR-005 | Sem regras locais no MVP | Mantém o escopo no transporte confiável de dados e comandos. |
| ADR-006 | WireGuard somente para a fase VPS | A rede externa não deve atrasar a validação do gateway local. |
| ADR-007 | Entrega pelo menos uma vez | Mais simples e robusta; deduplicação via IDs. |
| ADR-008 | Administração de dispositivo em serviço systemd separado, não no gateway (a interface já foi UI HTML, hoje é `DeviceAdminService` — ver ADR-015; o motivo abaixo não mudou) | `iot-gateway.service` roda sandboxed (`ProtectSystem=strict`, `ReadWritePaths` só a outbox) de propósito; registrar dispositivo exige escrever `/etc/mosquitto/*` e `gateway.yaml` e chamar `systemctl`, o que o processo do gateway nunca deve poder fazer. Mesmo motivo do updater já ser um serviço root separado. |
| ADR-009 | `internal/api` (não a API local inteira - ver ADR-013) dentro do processo `iot-gateway run`, não em serviço separado | Ao contrário do registro de dispositivo (ADR-008), publicar um comando só precisa da conexão MQTT que o gateway já mantém — abrir uma segunda conexão por requisição (como o CLI `publish-test-command` faz, aceitável por ser pontual) derrubaria repetidamente a sessão principal por colisão de `client_id`. Reaproveitar a conexão existente elimina o problema e não exige privilégio extra. Valia para `internal/commandapi` (removido) e vale do mesmo jeito para `internal/api`, que o substitui. |
| ADR-010 | Connect-RPC (`connectrpc.com/connect`) como transporte da API local, não gRPC puro | Uma única porta serve gRPC, gRPC-Web e HTTP/JSON — o último é o que faz `curl -d '{...}'` continuar funcionando sem cliente gRPC, sem perder o schema Protobuf nem a geração de stubs já usada em `api/proto`. |
| ADR-011 | Profile de device (`internal/deviceprofile`) valida `parameters` de comando contra Protobuf; MQTT continua JSON; device sem profile cai em fallback opaco (aposentado — ver ADR-016) | Sem schema, `{"on":"sim"}` publicava no MQTT sem erro e o firmware ignorava em silêncio. O profile é opt-in por dispositivo (`profile:` no YAML) para não obrigar toda a base existente a declarar um profile antes de continuar funcionando. |
| ADR-012 | `google.protobuf.Struct` em `PublishCommandRequest.parameters`, não `bytes *_json` como em `uplink.proto` | Em JSON, `bytes` vira base64 e quebraria `curl` e formulários simples — o ponto desta API. O custo é a precisão de número de `Struct` (decodifica como `double`); aceitável porque os parâmetros são validados e recodificados contra um schema Protobuf logo em seguida. Regra: parâmetro inteiro acima de 2^53 deve ser declarado `string` na mensagem do comando. |
| ADR-013 | `internal/apigateway`, dentro do processo `iot-gateway admin` (root), é a única borda pública de `api.address`; `internal/api` (dentro do `iot-gateway run` sandboxed) passa a escutar só `api.internal_address`, um endereço loopback, sem auth/CORS próprios | `DeviceAdminService` precisa acabar na mesma porta pública que `DeviceService`/`GatewayService` já usam, mas suas operações (escrever `gateway.yaml`, mexer no Mosquitto, `systemctl`) só podem rodar no processo root (ADR-008) — nunca no sandboxed. Dois processos não conseguem fazer `bind()` na mesma porta; um deles tem que encaminhar para o outro. É o processo admin (já root, já exposto na LAN em `:8081`) que fica com a porta pública, não o inverso, porque o processo sandboxed nunca deve ser quem decide repassar uma requisição para o processo com privilégio de root — inverter isso reabriria exatamente o problema que a ADR-008 fecha. Auth e CORS passam a existir só na borda (`internal/apigateway`); `internal/api` confia inteiramente no isolamento de loopback do sistema operacional, sem credencial própria. Encaminhamento por `httputil.ReverseProxy` genérico (bytes crus, sem decodificar RPC por RPC) - simples e suficiente enquanto não há streaming. |
| ADR-014 | `DeviceAdminService`: rollback automático só em `ProvisionDevice`, nunca em `RemoveDevice`; templates de provisionamento como registry compilado em `internal/admin`, não configurável em YAML (`ProvisionDevice` e seu template genérico aposentados — ver ADR-016; a postura de rollback vale do mesmo jeito para `ProvisionDeviceByIP`, que o substitui) | Desfazer uma credencial Mosquitto **recém-criada** (quando a escrita em `gateway.yaml` falha logo em seguida, no mesmo request) é seguro e de baixo risco. Desfazer uma **remoção** (recriar credencial + entrada no YAML automaticamente) é mais arriscado: pode reviver um device que o operador queria mesmo fora, então a falha vira erro + instrução manual, mesma postura que a UI HTML já tinha. Templates (só `esp32_led.v1` por enquanto) ficam em código, não em `gateway.yaml`, porque cada um fixa `type`/`profile`/tópicos de um hardware específico — não é um valor de configuração por instalação, é a definição de um kit suportado. |
| ADR-015 | Remover a UI HTML de admin (`:8081`); `DeviceAdminService` (via `gateway-web`) vira o único caminho de administração de dispositivo | `gateway-web` já implementa cadastro/habilitar-desabilitar/remoção sobre `DeviceAdminService` e foi validado de ponta a ponta em produção — a UI HTML parou de ter uma razão de existir só para redundância. `internal/admin` deixou de ter qualquer superfície HTTP própria: `*Server` agora é só o motor (`RegisterDevice`, `SetDeviceEnabled`, `DeregisterDevice`, etc.) que `internal/apigateway` já consumia via a interface `DeviceAdmin` — nada dessa lógica mudou, só a forma HTML de acessá-la foi apagada (`templates/`, `messages.go`, os handlers HTTP). `iot-gateway-admin.service` continua existindo e continua root (ADR-008 inalterada) — sem `api:` configurado, porém, ele agora recusa iniciar, já que não tem mais nenhum outro motivo para rodar. |
| ADR-016 | Aposentar `internal/deviceprofile`/`led.v1` (ADR-011) e as RPCs `ProvisionDevice`/`ProvisionCYD`/`ProvisionLED` (ADR-014) em favor do manifest genérico (`docs/device-manifests.md`) | Nenhum device em produção dependia mais do profile compilado — todos já provisionados pelo fluxo de manifest (Marco 4). `ProvisionCYD`/`ProvisionLED`/`ProvisionDevice` também já não eram chamados por nenhuma tela do `gateway-web` desde a migração do Marco 2 para `ProvisionDeviceByIP`; mantê-los apenas acumulava dois caminhos de validação/provisionamento paralelos para o mesmo resultado. `internal/deviceprofile`, o proto de `iot.device.led.v1` e os templates/RPCs específicos foram removidos; `RegisterExistingDevice` continua para adoção de serviço local (`orangepi_monitor.v1`), sem relação com este aposentamento. |
